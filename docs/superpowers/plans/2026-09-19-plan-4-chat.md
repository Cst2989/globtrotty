# Plan 4a — The Chat Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Deploy a Next.js chat on Netlify where the author signs in with a magic link, asks for a trip, watches the real agent run, and accepts or revises a proposal through buttons that travel on an operator channel the model cannot be talked into.

**Architecture:** Next.js App Router in the same package; reads through Supabase RLS with the user's cookie, writes through the existing repo functions on the owner connection inside route handlers; turns run in the existing Netlify background function, now on `routeAgent`. Button actions are `messages.role = 'action'` JSON rows hydrated into mid-conversation `system` messages. Row security is enable-only RLS with per-user policies. A deterministic outbound filter screens every agent message.

**Tech Stack:** Next 16.3, React 19.3, `@supabase/ssr` 0.12, `@supabase/supabase-js` 2.116, `@netlify/plugin-nextjs` 5.16, postgres.js, zod 4, vitest. Netlify CLI (logged in), Supabase CLI (logged in, project linked).

**Spec:** `docs/superpowers/specs/2026-09-19-plan-4-chat-design.md`, narrowing `docs/superpowers/specs/2026-08-15-globetrotty-design.md` §6, §7, §9, §10 (binding).

## Global Constraints

- `user_id` comes from the verified Supabase session in every route handler, never from a request body. Browser reads go through RLS with the anon key; server writes go through `DATABASE_URL` (owner) in route handlers only. `SUPABASE_SERVICE_ROLE_KEY` is never imported by `app/` or `web/`.
- Only `recordSpend`, `reserve`, `reconcile` move money; nothing in this plan touches them.
- Agent and user text render as plain text; no markdown, no linkification. The only anchors are `link_clicks.url`.
- Button actions are never user text: they are `role = 'action'` rows written only by route handlers, hydrated as `role: 'system'` transcript messages. `messages.role` check: `user | agent | action`.
- `withSuffix` appends the notebook to the LAST USER message even when a `system` message follows it. A request never has a user turn after a mid-conversation system turn.
- RLS: enable-only with policies; never `force row level security` (the worker is the owner; see 0003's warning). `authenticated` gets `select` only on the tables the spec lists; no write grants; `anon` gets nothing.
- Every agent message passes `screenOutbound` before `completeTurn`.
- No new REQUIRED env key in `src/env.ts` `KEYS`. `GOOGLE_SEARCH_API` is optional via `loadOptionalEnv`. `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` are the only `NEXT_PUBLIC_` names.
- Never edit migrations 0001–0015. New DDL is `0016_plan_4_chat.sql`.
- `pnpm test && pnpm typecheck && pnpm lint && pnpm build` clean before every commit. Commit messages end with the session's attribution lines.
- Every rule gets the break-and-watch-it-fail check; the plan names the break per test.

## Deviations, decided while planning

1. RLS is enabled with policies, not forced (spec 4a §8).
2. The Next.js app owns the root `tsconfig.json` (Next rewrites it); the harness typechecks with `tsconfig.harness.json` (NodeNext, `src`/`test`/`netlify`). `pnpm typecheck` runs both. ESLint ignores `app/`, `web/`, `.next/` (its Babel parser has no JSX preset and the money rule is scoped to `src/repo/**`).
3. Migration 0016's Realtime publication change is conditional on the `supabase_realtime` publication existing, and `supabase/ci-bootstrap.sql` creates a stub `auth.uid()` so the policies apply on the CI container. The two-user isolation test runs only against Supabase (`LIVE_SUPABASE=1`).
4. Component rendering is tested with `react-dom/server`'s `renderToStaticMarkup` (no jsdom, no testing-library).

```sql
-- Supabase's auth.uid() reads the JWT claim GoTrue sets per request. A bare Postgres
-- has no auth schema, so policies referencing auth.uid() would fail to CREATE. This
-- stub returns NULL (no session) so the migrations apply and the owner-connected
-- tests are unaffected; the real isolation test runs against Supabase only.
create schema if not exists auth;
create or replace function auth.uid() returns uuid language sql stable as $$
  select nullif(current_setting('request.jwt.claim.sub', true), '')::uuid
$$;
```

- [ ] **Step 3: Migration**

```sql
-- supabase/migrations/0016_plan_4_chat.sql
--
-- Plan 4a. Four changes, all for the browser client that now exists.
--
-- 1. messages.role gains 'action': a button press (accept / reject / revise) stored
--    as a JSON row written only by route handlers, hydrated by the worker into a
--    mid-conversation SYSTEM message. Never user text, so never forgeable by text.
-- 2. agent_events.kind gains 'screened': an agent reply the outbound filter replaced.
-- 3. Realtime: conversations and messages join the publication so the browser
--    can refetch on change. Conditional: the CI container has no publication.
-- 4. Row security for the browser: enable-only RLS (0003) with SELECT policies for
--    `authenticated` on user-owned tables. NOT forced — the worker is the owner,
--    and 0003 documents why forcing would break the global ceiling's sum. No
--    write grants: every write is a route handler on the owner connection.

alter table messages drop constraint messages_role_check;
alter table messages add constraint messages_role_check check (role in ('user','agent','action'));

alter table agent_events drop constraint agent_events_kind_check;
alter table agent_events add constraint agent_events_kind_check
  check (kind in ('tool_start','tool_done','thinking','parked','failed','continued','screened'));

do $$ begin
  if exists (select 1 from pg_publication where pubname = 'supabase_realtime') then
    alter publication supabase_realtime add table conversations, messages;
  end if;
end $$;

-- Reads for the signed-in traveller. `authenticated` had every privilege revoked in
-- 0003; this grants SELECT back on exactly the tables the app renders from.
grant select on conversations, messages, turns, proposals, link_clicks, agent_events,
                escalations, tool_results, gate_results to authenticated;

create policy own_conversations on conversations for select to authenticated using (user_id = auth.uid());
create policy own_messages      on messages      for select to authenticated using (user_id = auth.uid());
create policy own_turns         on turns         for select to authenticated using (user_id = auth.uid());
create policy own_proposals     on proposals     for select to authenticated using (user_id = auth.uid());
create policy own_link_clicks   on link_clicks   for select to authenticated using (user_id = auth.uid());
create policy own_agent_events  on agent_events  for select to authenticated using (user_id = auth.uid());
create policy own_escalations   on escalations   for select to authenticated using (user_id = auth.uid());
create policy own_tool_results  on tool_results  for select to authenticated using (user_id = auth.uid());
-- gate_results carries no user_id (0004): join through the conversation.
create policy own_gate_results  on gate_results  for select to authenticated
  using (exists (select 1 from conversations c where c.id = gate_results.conversation_id and c.user_id = auth.uid()));

-- RLS must be ENABLED on every table that now carries a policy; 0003/0004/0014/0015 did
-- this for most. Idempotent for the rest.
alter table turns        enable row level security;
alter table agent_events enable row level security;
alter table escalations  enable row level security;
```

export const ActionPayload = z.discriminatedUnion('action', [
  z.strictObject({ action: z.literal('hand_off'), proposalId: z.uuid() }),

                     z.strictObject({ kind: z.literal('shift'), days: z.union([z.literal(-2), z.literal(2)]) })]) }),

Call revise_component with { kind: 'shift', days: <days> }; if the corpus lacks those dates it will tell you to search them first — do so, then revise.`
