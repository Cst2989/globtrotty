Globetrotty · Implementation record

A travel agent that survives being killed

The foundation is built and running against a live database: a durable-execution harness that can lose power mid-booking, get double-invoked, or have two workers fight over the same turn, and still do exactly the right thing once. No model is wired in yet. This is the layer everything else stands on.

Status

What exists today

Honest summary first, because the interesting part of this project is not yet the part people expect. There is no chat interface and no model call. What there is, is the machinery that makes a chat interface safe to build: a request tier that never blocks, a worker that can be killed at any instruction, and a sweeper that finds whatever got dropped.

Shape

Four tiers, because the platform has four budgets

The architecture is not a preference. Netlify gives a synchronous request about ten seconds, a background function fifteen minutes, and a scheduled function thirty. A travel search that fans out across suppliers and reviews its own work does not fit in ten seconds, so the work has to leave the request. Once it leaves, it has to be recoverable — which is the entire reason the rest of this document exists.

Tier 1 Browser — Posts a message. Subscribes to the conversation and watches rows change.
→
Tier 2 Request handler ~10 s Checks spend, writes the message, opens one turn, returns. Does no model work at all.
→
Tier 3 Background worker 15 min Claims the turn, runs the loop, heartbeats while it thinks, saves state after every step.
→
Tier 4 Sweeper 30 s Runs on a schedule. Finds turns nobody is working on and puts them back in the queue.
The loop back is the point. The sweeper does not report failures — it repairs them. A turn whose worker died is indistinguishable from a turn whose worker is slow, so the only honest test is silence: ninety seconds without a heartbeat and the turn is fair game again. Everything else in the harness exists to make that reclaim safe.
Guarantees

What the harness actually promises

Five properties, each with a mechanism rather than an intention. All five are covered by tests, and all five are demonstrable in one command against the real database.

  1. 01
    Pressing send fifty times buys one turn. A partial unique index allows exactly one turn per conversation in queued or running. A retried request with the same idempotency key reads back the turn it already created; a genuinely new message arriving mid-flight is stored for the running turn to pick up, never dropped.
  2. 02
    Two workers cannot both write. Claiming increments attempts, and every subsequent write carries that number in its WHERE. A worker that was superseded while it was thinking updates zero rows and raises rather than silently doing nothing — the fencing token is the attempt counter itself, so there is no second thing to keep in sync.
  3. 03
    A tool with side effects runs once across a crash. Intent is written before the effect. On resume, a finished call replays its stored result and a call that died mid-effect is reported as ambiguous — escalated rather than guessed, because nothing can tell you whether the email went out.
  4. 04
    The spend ceiling fails closed. The usage read throws rather than returning zero when the database cannot confirm the number. A ?? 0 there would disable the guardrail at the exact moment it is most needed. Ceilings are checked before every call, not once per turn.
  5. 05
    A turn cannot end half-written. Finishing a turn writes its state, status, spend, the agent's message, and the conversation's status in one transaction. The earlier version wrote them separately, which left done turns with no message and conversations stuck on working forever — the sweeper only rescues live turns, so nothing would ever have found them.
Run it

Seeing it work

The demo is narrated and runs against the live Supabase instance. It kills a turn mid-tool-call, waits for the sweeper, resumes it on a fresh worker, and counts side effects to prove the tool ran exactly once. Then it stages two workers against one turn and shows the loser's write being rejected. 

npm test        # 102 tests, 12 files
npm run demo    # narrated tour against the real database
npm run typecheck

Everything the demo writes is scoped to one fixed user id and deleted at both ends, so it is safe to run repeatedly.

Findings

What the reviews changed

The foundation was built task by task, each one implemented by a fresh agent and reviewed by another, then reviewed once more across the whole branch. That last review is the one that earned its keep.

Three defects only a whole-branch review could see

Every per-task review passed. The seams between tasks did not. The heartbeat was never actually emitted during a step; the continuation path saved state without releasing ownership, so a resumed turn could never claim itself; and a failure path left the attempt counter somewhere no reaper would look.

All three were invisible under the echo agent used for testing, because nothing it did took long enough to matter. They would have surfaced the first time a real model call ran past ninety seconds.

A recurring pattern worth naming

Across twelve tasks, the implementations were almost always right and the tests were the weak point. Four separate findings were tests that would have passed against a wrong implementation: an unpinned precedence order, a fenced test that short-circuited on its first statement, a concurrency test quietly serialised by a connection limit, and a guard that needed tracing before anyone could confirm it discriminated at all.

Sixteen notes back into the articles

Building the harness from the source articles surfaced defects in the articles themselves. Those are recorded in place as HTML comments — invisible when rendered, greppable with grep -rn "REVIEW(globetrotty)" docs/. Thirteen are in part two.

The heaviest one: the provenance check validates identity but never values. A model can cite a real hotel with a real source id and attach a price it invented; provenance passes, and the budget check then dutifully validates the invented number. The second: the drift-detection advice compares response.model against what was requested — but for an aliased model the API echoes the alias back verbatim, confirmed against the live endpoint, so every trace row reads identically before and after a weights change.

Next

What comes next

Three plans remain, in order. Each produces something testable on its own.

Suppliers and gates

A supplier port with a mock behind it, the Kiwi adapter for flights, and the gate stack: rehydration, freshness, currency, totals, budget, dates. Both live sources are now verified and keyed, and the pre-tax-versus-total split that SearchApi returns is exactly the seam a totals gate exists to catch. This plan also implements the global daily ceiling, which the foundation defines but deliberately leaves unenforced.

The fleet

Front desk, planning loop, scouts, reviewer, cashier — and the first real model call. Two changes to the harness are required here and already recorded: the agent step must run inside the heartbeat wrapper, and the agent type needs an abort signal. Both are unreachable under an echo agent and both become live the moment a frontier model or a supplier sweep runs past ninety seconds.

The interface

The chat itself: a sidebar of trips named after their destination, proposal cards with per-component accept and reject, a split channel so the agent's progress is visible while it works. Plus row-level security policies with a two-user isolation test, since the lockdown migration currently revokes access rather than scoping it.
